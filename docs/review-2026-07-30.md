# Projekt-Review – support.sheet (2026-07-30)

Vollständiges Review des gesamten Projekts: ursprüngliches Cheatsheet (index/exchange/forti/scripts/tools/mitmachen),
Analyzer-Tools (eventlog/entra/har), guide.sheet-Subsystem (Phase 1–8), PowerShell-Skripte,
Service Worker/Manifest und Datenfiles.

**Nur Analyse – es wurde nichts verändert.** Fundstellen sind mit Datei + Zeile zitiert, damit sie direkt
nachvollziehbar sind. Severity-Einstufung (🔴 Hoch / 🟡 Mittel / ⚪ Niedrig) orientiert sich am
tatsächlichen Bedrohungsmodell dieser App: **kein Backend, kein Login, Single-User, lokal.** Die relevante
Angriffsfläche ist praktisch ausschließlich: *„Was passiert, wenn ich eine Datei öffne, die jemand anders mir
geschickt hat?"* (HAR-Export, Entra-Sign-In-Log, DOCX-Import, Guide-Merge-Paket-ZIP) – das ist ein sehr
realistisches Szenario für IT-Support-Alltag (Kunde/Kollege schickt einen Log zur Analyse).

---

## 1. Architektur-Überblick

- Kein Framework, kein Build-Schritt – reines HTML/CSS/JS, läuft komplett clientseitig als PWA (Service Worker
  `sw.js`, `manifest.json`).
- Zwei große Bereiche:
  1. **Cheatsheet** (`index.html`, `exchange.html`, `forti.html`, `scripts.html`, `tools.html`, `mitmachen.html`)
     – Referenzdaten aus `data/*.json`, gerendert über `js/render.js` + Konsorten.
  2. **guide.sheet** (`guides*.html`, `js/guides-*.js`) – lokale Wissensdatenbank mit File System Access API
     (Chrome/Edge) bzw. IndexedDB-Fallback (Firefox/Brave), inkl. Editor, Export/Import als ZIP, Papierkorb.
  3. **Analyzer-Tools** (`eventlog.html`, `entra.html`, `har.html`) – Import von Log-/HAR-Dateien, lokale Analyse
     gegen Regel-JSONs.
  4. **PowerShell-Skripte** (`powershell/*.ps1`) – zum Download, laufen auf den Rechnern der Nutzer, nicht im Browser.
- Gemeinsame Navigation (`nav.js`) und Design-Tokens (`css/main.css`) binden alles zusammen.
- Kein Server, keine Telemetrie, keine externen API-Calls außer: Google Fonts (Fallback, Service Worker cached
  es), und der `ticketassistent.html`-iframe (siehe 2.8).

## 2. Sicherheit – Funde

### 2.1 🔴 XSS via `innerHTML` in den Analyzer-Tools (HAR/Entra/EventLog)

Alle drei Analyzer bauen Tabellenzellen mit farbigen Status-Badges über String-Templates und setzen sie per
`innerHTML`, statt sie sicher per `textContent`/`createElement` aufzubauen – **mit Feldwerten direkt aus der
hochgeladenen Datei, ungeprüft und unescaped:**

- **`js/entra.js:434`** (`renderTable`):
  ```js
  const status = F.status(r);   // = getField(r, 'Status')  – js/entra.js:162
  const code   = F.code(r);     // = getField(r, 'Code des Anmeldefehlers') – js/entra.js:163
  ...
  { html: `<span class="${statusCls}">${status}</span>` },
  { html: code && code !== '0' ? `<span class="err-code">${code}</span>` : '' },
  ```
  `getField()` liest die Werte **direkt aus dem geparsten JSON der hochgeladenen Entra-Sign-In-Logs**, ohne
  Allowlist/Escaping. Eine Log-Datei mit `"Status": "<img src=x onerror=alert(document.cookie)>"` führt beim
  Öffnen im Entra Analyzer zur Codeausführung im Kontext von support.sheet.

- **`js/har.js:377` und `:400`**:
  ```js
  { html: `<span class="${statusCls(r.status)}">${r.status}</span>` },
  ```
  `r.status` stammt aus `en.response?.status || 0` (`js/har.js:115`) – **kein `Number()`-Cast**. Eine
  präparierte HAR-Datei (reines JSON, mit jedem Texteditor änderbar) mit `"status": "<script>...</script>"`
  triggert dieselbe Lücke.

- **`eventlog.html:1595`** (Haupt-Ereignistabelle):
  ```js
  { html:`<span class="lv lv-${lvl}">${e.Level||'Info'}</span>` },
  ```
  `e.Level` kommt direkt aus der hochgeladenen Collector-JSON. Ebenso `eventlog.html:734–737`
  (Auth-Tabelle) mit `e.Id` – dort zwar mit `Number(e.Id)` geprüft, aber der interpolierte Wert im
  `else`-Zweig ist weiterhin der **rohe, ungeprüfte** `e.Id`-Wert, nicht das gecastete Ergebnis.

**Warum relevant trotz Single-User-App:** Diese Tools sind explizit dafür gedacht, Dateien zu analysieren,
die man von einem Kunden/Kollegen bekommt ("schau mal in den Log/HAR"). Das ist der einzige Trust-Boundary
dieser App, und genau dort liegt die Lücke.

**Fix-Empfehlung:** Für alle vier Stellen den gleichen sicheren Pattern verwenden, der im selben File für die
*meisten anderen* Zellen bereits korrekt eingesetzt wird (`td.textContent = ...`). Für die farbigen Badges:
Klasse und Text getrennt setzen statt Template-String:
```js
const span = document.createElement('span');
span.className = statusCls; // kontrollierter Wert, kein User-Input
span.textContent = status;  // escaped automatisch
td.appendChild(span);
```

### 2.2 🟡 XSS via `marked.js` (kein HTML-Sanitizing) in guide.sheet

`js/guides-view.js:188` und `js/guides-editor.js:246` rendern Guide-Inhalt/Vorschau via
`preview.innerHTML = marked.parse(...)`. **`marked.js` sanitisiert standardmäßig kein eingebettetes HTML** –
Markdown, das rohes `<script>` oder `<img onerror=...>` enthält, wird 1:1 durchgereicht und ausgeführt.
Es gibt keinen `marked.setOptions(...)`-Aufruf und keine DOMPurify-Einbindung im ganzen Projekt (geprüft).

**Warum relevant:** guide.sheet hat explizit eine **Import/Merge-Funktion für ZIP-Pakete von anderen
Nutzern** (`js/guides-manage.js`, Phase 7/8) und einen DOCX-Import (mammoth → Turndown). Ein Merge-Paket
mit präpariertem `content.md` (`<img src=x onerror=...>`) führt beim Öffnen des importierten Guides zur
Codeausführung. Das ist exakt das im Konzept-Dokument beschriebene Zukunfts-Feature „Guide-Pakete" (öffentlich
teilbare Guide-Sets) – dort wäre der Angriffsvektor noch direkter.

**Fix-Empfehlung:** `js/marked.min.js` mit einem Sanitizer kombinieren (z. B. DOMPurify lokal einbinden, wie
bei den anderen Libraries auch – kein CDN) und `DOMPurify.sanitize(marked.parse(md))` statt direktem
`innerHTML` verwenden. Minimal-Alternative ohne neue Dependency: `marked.parse(md, { sanitize: true })` ist
in aktuellen marked-Versionen entfernt/deprecated – daher wirklich eine externe Sanitize-Bibliothek nötig.

### 2.3 🟡 Fehlende ID-Validierung beim ZIP-Import (guide.sheet)

`js/guides-manage.js:272` (`parseMergePackage`) extrahiert die Guide-ID direkt aus dem ZIP-Pfad:
```js
const m = path.match(/^guides\/([^/]+)\/meta\.json$/);
```
`[^/]+` erlaubt theoretisch auch `..` als „ID". Diese ID wird später unverändert an
`GuidesDB.saveGuide(targetId, ...)` gereicht, was im Filesystem-Modus zu `root.getDirectoryHandle(id, {create:true})`
führt (`js/guides-db.js`). Die File System Access API lehnt `..`/`.`/Namen mit `/` normalerweise selbst ab
(spec-seitige Namensvalidierung), sodass dies vermutlich bereits von der Browser-API abgefangen wird – das
Projekt verlässt sich hier aber **allein auf diese Plattform-Garantie**, ohne eigene Defense-in-Depth-Prüfung.
`saveGuide()`/`getGuide()`/`deleteGuide()` in `js/guides-db.js` validieren `id` nirgends gegen ein erwartetes
Muster (nur `if (!id)`-Check, `js/guides-db.js:279`).

**Fix-Empfehlung:** Vor der Verwendung importierter IDs ein Pattern erzwingen, z. B.
`/^guide-[a-zA-Z0-9_-]+$/`, sonst Import dieses Eintrags mit Fehlermeldung überspringen.

### 2.4 🔴 Client-Secret landet im Klartext-Transkript-Log (`M365-Setup-AppRegistration.ps1`)

`Start-Transcript -Path $LogPath` (Zeile 58) zeichnet die gesamte Konsolenausgabe auf. Das neu erzeugte
Client-Secret wird per `Write-Host` in der „nur EINMAL sichtbar"-Box ausgegeben (Zeilen 541–546) – landet
dadurch **vollständig und dauerhaft** in `M365-Setup-Log-<timestamp>.log`, nicht nur auf dem Bildschirm.
Diese Logs werden erfahrungsgemäß für Troubleshooting aufgehoben/weitergegeben.

**Fix-Empfehlung:** Secret vor der Ausgabe maskieren (nur letzte 4 Zeichen zeigen) oder Transcript kurz
pausieren (`Stop-Transcript` / `Start-Transcript` um den Secret-Ausgabe-Block herum), und im Skript-Output
explizit warnen, dass die Log-Datei sensibel ist.

### 2.5 🟡 App-Secret wird unverschlüsselt auf Platte gespeichert

`M365-Setup-AppRegistration.ps1:583`: `$AppConfig | ConvertTo-Json | Set-Content -Path $TenantCfgPath` –
das Secret (Zeile 580) landet als Klartext-JSON auf der Platte. Jeder mit Dateisystem-Zugriff (inkl.
OneDrive-Sync/Backup) bekommt damit ein tenant-weites Credential mit **SharePoint Administrator +
Exchange Administrator**-Rollen (siehe 2.6).

**Fix-Empfehlung:** `Export-Clixml` (DPAPI-geschützt, an Benutzer/Maschine gebunden) statt rohem JSON, oder
zumindest deutliche Warnung + Empfehlung, die Datei aus Backups/Sync auszuschließen.

### 2.6 🟡 Breite, dauerhafte Rollenvergabe + ungenutzte Permissions

`M365-Setup-AppRegistration.ps1` vergibt der Service-Principal **SharePoint Administrator** (Zeile 616–644)
und **Exchange Administrator** (Zeile 646–675) als Directory Roles – für ein als „Read-Only-Inventory-Tool"
beschriebenes Skript. Ein kompromittiertes Secret bedeutet damit tenant-weite Admin-Rechte. Zusätzlich wird
`Organization.ReadWrite.All`/`ReportSettings.ReadWrite.All` anfordert (Zeilen 90–91), aber **nirgends in
`M365-Inventory.ps1` tatsächlich genutzt** (verifiziert per grep) – totes Overprovisioning, das nur unnötig
Risiko erhöht, falls das Secret geleakt wird.

**Fix-Empfehlung:** Rollen/Scopes minimieren, ungenutzte Write-Permissions entfernen, Rollenvergabe im
Skript-Output klar kommunizieren + zur regelmäßigen Prüfung/Rotation auffordern.

### 2.7 ⚪ Kein Content-Security-Policy

Keine der HTML-Seiten setzt einen CSP-Meta-Tag (geprüft, keine Treffer). Für eine reine Client-Anwendung ohne
Server wäre ein `<meta http-equiv="Content-Security-Policy" ...>` mit strikter `script-src`/`object-src`
sinnvolle Defense-in-Depth gegen genau die unter 2.1/2.2 gefundenen XSS-Klassen – würde deren Ausnutzung
zusätzlich erschweren, auch nach einem Code-Fix.

### 2.8 ⚪ Ticketassistent-iframe (Kontext, kein akutes Problem)

`ticketassistent.html:83–90` bindet `https://jluenthus.github.io/Ticketassistent/` per iframe ein, mit
`allow="clipboard-write clipboard-read"` und ohne `sandbox`-Attribut. Funktional nötig (Copy/Paste ins
Ticketsystem), aber es bedeutet: support.sheet vertraut vollständig der Integrität dieser separat gehosteten
Seite. Kein Sicherheitsfehler, aber eine Abhängigkeit, die im Hinterkopf behalten werden sollte (Domain/
GitHub-Account-Absicherung des Zielprojekts).

## 3. Kritische/sensible Daten

- **Keine Zugangsdaten oder Kunden-/interne Hostnamen in den JSON-Datenfiles** – von zwei Agents unabhängig
  geprüft (`data/*.json`, `commands.json`, `entra-rules.json` etc.). Alle Treffer für „password"/„secret"/IP
  sind erkennbare Platzhalter/Doku-Beispiele (`8.8.8.8`, `BENUTZERNAME`, `NeuesPasswort!123` etc.).
- **`localStorage`-Inventar** (alles unverschlüsselt, wie für eine Client-PWA erwartbar, aber hier
  dokumentiert):
  - `adminsheet_favorites`, `adminsheet_recent_commands` (`js/recent.js:6`) – letzteres speichert **den
    aufgelösten Befehl inkl. eingesetzter Werte** (Domain/Server/Username, falls über `{platzhalter}`
    ausgefüllt) im Klartext, capped auf 5 Einträge.
  - `supportsheet_settings` (`js/settings-store.js:7`) – Default-Domain/Server/Username. Niedrige
    Sensitivität (interne Infrastruktur-Metadaten, keine Credentials), aber unverschlüsselt auch im
    Backup-Export (`js/tools.js:135–164`) enthalten, der als Datei auf die Platte geschrieben wird.
  - `gs-draft`, `gs-export-name`, `gs-last-export`, `gs-howto-hint-dismissed` (guide.sheet) – Entwürfe
    können jetzt auch Bilder als Base64 enthalten (Fix aus dieser Session), landen ebenfalls unverschlüsselt
    in `localStorage`.
  - guide.sheet-Kategorie **„Kunden"** ist laut Konzept-Dokument explizit für „persönliche Kundennotizen"
    vorgesehen – bewusst lokal, unverschlüsselt (File System Access API bzw. IndexedDB). Kein Bug, aber
    erwähnenswert: Wer diesen Ordner synced (OneDrive/Backup) oder ein Merge-Paket exportiert, gibt
    Kundennotizen im Klartext weiter. Das Konzept-Dokument selbst merkt das für Export bereits an
    ("Keine automatische Filterung von Kundendaten... Zukünftig: Tag `kunde:*` automatisch ausschließen").
- **`Get-EventLogCollector-*.ps1`** schreibt Security-Event-Log-Inhalte (ggf. Kontonamen in `Message`-Feldern)
  unverschlüsselt nach `C:\Temp\EventLog_*.json` – ein für alle lokalen Nutzer lesbarer Pfad auf
  Mehrbenutzer-Systemen. Kein automatischer Upload, aber der Ablagepfad ist nicht gehärtet.
- **Keine sensiblen Daten werden geloggt** (console.*) – einzige Ausnahme ist Debug-Spam (siehe 4.5), aber
  ohne sensiblen Inhalt.

## 4. Code-Qualität & Bugs

1. **`Test-NetworkConnectivity.ps1:48`** – `foreach ($host in $targets.Keys | Sort-Object)`: `$host` ist
   PowerShells reservierte, schreibgeschützte Automatik-Variable. **Verifiziert: Das Skript führt dadurch
   aktuell gar keinen einzigen Verbindungstest aus** – die Schleife wirft bei jedem Durchlauf einen Fehler
   und das Ergebnis ist immer „0/0 Tests erfolgreich". Umbenennen zu z. B. `$targetHost` (Zeilen 48–88).

2. **`mitmachen.html:545`** – `MAIL_TO = 'deine@email.de'` ist ein nicht ausgefüllter Platzhalter. Das
   komplette „Mitmachen"-Formular ist dadurch aktuell funktionslos (mailto geht an eine Fake-Adresse).

3. **JSON-Escaping-Bugs in `mitmachen.html`**: `updatePreview()`/`submitBefehl()` (Zeilen 559–578, 736–795)
   escapen nur `"`, nicht Zeilenumbrüche/Backslashes – bei mehrzeiliger Beschreibung entsteht ungültiges
   JSON. `updatePreviewScript()` (Zeile 588–591) escaped nicht mal Backslashes, obwohl PowerShell-Beispiele
   (`.\Skript.ps1`, `C:\Temp\...`) das routinemäßig enthalten – inkonsistent zu `updatePreview()`, das es
   richtig macht (Zeile 567).

4. **`scripts.html:225–226`** – zwei öffnende `<footer>`-Tags, nur ein schließendes (Zeile 235). Browser
   korrigiert das automatisch, aber ungültiges Markup.

5. **`js/loader.js:39–48`** – loggt bei jedem Seitenaufruf alle 241 Commands einzeln in die Konsole. Reiner
   Debug-Rest, sollte entfernt oder hinter einen Debug-Flag gesetzt werden.

6. **Fehlende Validierungskonsistenz** (`js/tools.js` vs. `js/variables.js`): Default-Domain/Server/Username
   werden beim Speichern (`tools.js:11–28`) nur getrimmt, aber erst beim späteren Einsetzen ins
   `{platzhalter}` gegen `SAFE_VALUE_REGEX` geprüft (`variables.js:56`). Nutzer merkt ungültige Zeichen also
   erst viel später als nötig.

7. **`js/tools.js` Import (`importData`, Zeile 169–216)** prüft nur `Array.isArray`, keine
   Objekt-Shape-Validierung pro Eintrag. Ein kaputtes Backup-JSON (`recent: [null]`) kann später in
   `js/render.js:272–284` (`entry.id` etc. ohne Null-Guard) zum Absturz führen.

8. **`sw.js`** cached `.ps1`-Skripte „Cache First" (wie andere JS-Assets), nicht „Network First" wie HTML.
   Wird ein Bug in einem heruntergeladenen Skript gefixt (z. B. Fund #1 oben) **ohne** `CACHE_VERSION` zu
   bumpen, bekommen Nutzer mit bereits installierter PWA dauerhaft die alte, kaputte/unsichere Version.
   Zusätzlich fehlen `M365-Inventory.ps1` und `M365-Setup-AppRegistration.ps1` in der `ASSETS`-Precache-Liste
   (Zeilen 7–88) – kein Sicherheitsbug, aber Inkonsistenz.

9. **`Exchange-PreflightCheck.ps1`** – `-ApplyMaintenance`-Gate prüft nur `$script:FailCount`, nicht
   `$script:WarnCount` (Zeile 330). Volle Mail-Queues oder hoher Replikations-Lag (nur „WARN") verhindern
   das Draining/Suspend eines Exchange-Servers dadurch **nicht**, obwohl die Zusammenfassung selbst das als
   „nicht ALLES OK" einstuft.

10. **`Set-PowerPlan-Win11.ps1`** – kein `#Requires -RunAsAdministrator`, obwohl Registry/WMI-Schreibzugriffe
    (Zeilen 221–238) Admin-Rechte brauchen. Schlägt ohne klare Fehlermeldung fehl, wenn nicht elevated
    gestartet.

11. **`Get-InstalledSoftware.ps1` / `Get-SystemInventory.ps1`** – bauen den HTML-Report per String-
    Konkatenation ohne HTML-Encoding der Feldwerte (`DisplayName`, `Publisher` etc.). Niedriges Risiko
    (lokale Software-Metadaten), aber technisch dieselbe Fehlerklasse wie 2.1.

12. **Duplizierte Loader-Logik** in `exchange.html:137–174` und `forti.html:138–173` – fast identischer
    Inline-Script-Block, nur JSON-Pfad unterschiedlich. Kandidat für eine gemeinsame parametrisierte Funktion.

13. **Fehlender Focus-Trap** im Doku-Modal (`tools.html`) – Tab kann während offenem Modal aus dem Dialog
    heraus navigieren; nur Escape/Close-Button sind verdrahtet.

## 6. Was gut gemacht ist

- **Cheatsheet-Kernapp ist durchgehend sauber** in Sachen XSS: praktisch überall `textContent`/`createElement`
  statt `innerHTML`, sogar mit Kommentaren, die das bewusst dokumentieren (`recent.js:76`, `tools.js:4`,
  `variables.js:3`) – das ist erkennbar absichtliches, gutes Sicherheitsdesign, nur in den später gebauten
  Analyzer-Tools (2.1) und guide.sheet (2.2) nicht konsequent durchgehalten worden.
- `js/variables.js` hat mit `SAFE_VALUE_REGEX` eine durchdachte Injection-Abwehr für Shell-Metazeichen beim
  Befehle-Kopieren.
- `js/tools.js` nutzt für den Doku-Modal-Fetch eine harte `DOC_WHITELIST` statt beliebige Pfade zuzulassen.
- Destruktive PowerShell-Skripte (`Exchange-PreflightCheck.ps1`, `Set-BraveDebloat.ps1`,
  `Set-PowerPlan-Win11.ps1`) haben durchweg Bestätigungs-/Preview-Flows eingebaut, bevor etwas geändert wird.
- `M365-Inventory.ps1` ist sauber read-only, loggt Token-Länge statt Token-Inhalt, keine unerwarteten
  Netzwerk-Ziele.
- Datenfiles (`data/*.json`) sind vollständig frei von echten Zugangsdaten/internen Hostnamen – für ein
  öffentliches Repo genau richtig.
- sw.js Cache-Versionierung und Fetch-Strategie (Network-First für HTML, Cache-First für Assets) ist ein
  solides, korrektes PWA-Pattern – die einzige Einschränkung ist die fehlende Sonderbehandlung für
  herunterladbare Skripte (4.8).
